# Supplied Skills Corpus — Document Path Findings

The supplied sample archive contains six project skills. All six contain path literals that would need to change when a repository normalizes project knowledge under `documents/`.

The archive is used as a detection/test corpus only; the Project Structure Architect skill does not assume these exact skills exist in every project.

## Skills requiring updates

| Skill | Main legacy paths found | Canonical mapping | Additional review |
|---|---|---|---|
| `document-task` | `documentation/AGENTS.md`, `documentation/0-index.md`, `documentation/application/**`, `documentation/agent-observations/**`, `docs/tasks/**` | `documents/documentation/**`, `documents/tasks/**` | Re-read routing rules after rewrite so documentation and task lifecycle remain separate |
| `execute-plan` | `docs/tasks/lessons-active.md` | `documents/tasks/lessons-active.md` | Verify any task evidence/log paths generated by companion skills/helpers |
| `one-shot-documentation` | `docs/tasks/planning/**`, `documentation/0-index.md`, `documentation/application/**`, `documentation/project-overview.md`, `documentation/agent-observations/**`, `documentation/agents/**` | `documents/tasks/**`, `documents/documentation/**` | **Semantic review required:** policy language that allows task ledgers, QA evidence, migrations, backups, or logs beneath the documentation root should be reclassified against the sibling `documents/*` namespaces rather than mechanically preserved |
| `plan-task` | task-system config, verification config/capabilities, lessons files, task-system helper script under `docs/tasks/**`; `documentation/0-index.md` | `documents/tasks/**`, `documents/documentation/0-index.md` | Verify helper scripts create plan folders under the new task root |
| `task-manager` | `docs/tasks/task-system.config.yaml`, `docs/tasks/verification-system.config.yaml` | `documents/tasks/**` | Verify any dynamically resolved task paths from config use the canonical root |
| `update-documentation` | `docs/tasks/planning/**`; `documentation/0-index.md`, `documentation/application/**`, `documentation/project-overview.md`, `documentation/agents/**` | `documents/tasks/**`, `documents/documentation/**` | Preserve its ownership boundary: current documentation belongs to documentation; task lifecycle remains under tasks |

## Canonical namespace used by the updated skill

```text
documents/
├── documentation/
│   ├── 0-index.md
│   ├── project-overview.md
│   ├── application/
│   ├── architecture/
│   ├── specifications/
│   ├── decisions/
│   └── agent-observations/
├── tasks/
│   ├── planning/
│   ├── evidence/
│   └── existing task-system config/helpers/lessons
├── research/
├── audits/
├── reports/
├── notes/
└── archive/
```

The important migration rule is to **preserve each installed subsystem's internal topology first** while normalizing its root. For example, `docs/tasks/task-system-helpers/create-plan-folder.py` becomes `documents/tasks/task-system-helpers/create-plan-folder.py`; the task system itself is not redesigned unless that is separately requested.

## Verification expectation

After an apply-mode migration, rerun the document-path audit and verify:

- no stale `documentation/**` path literals remain where they refer to the old root;
- no stale `docs/tasks/**` path literals remain;
- no installed skill or helper recreates those roots;
- skill installation paths such as `.agents/skills/update-documentation/SKILL.md` are unchanged;
- external URLs containing `/documentation/` are unchanged;
- path-policy language still assigns task/evidence/report/audit material to the correct `documents/*` namespace.
